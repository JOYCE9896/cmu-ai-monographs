第六讲：编程 Agent

从补全一段代码，到在真实仓库里定位、修改、验证，再到整个软件开发流程

主讲：Graham Neubig · 2026 年 9 月 10 日
资料来源：课程幻灯片 · 课堂录像

一、编程 Agent 的三个层次

编程是目前 Agent 用得最多、也最成熟的领域。课程把它分成三个层次：第一层是写代码，一次补全一段；第二层是修改仓库，同时改动多个文件；第三层是参与开发，覆盖软件的整个生命周期。一个编程 Agent 由三样东西组成：提示词、工具、LLM。这一讲先讲模型怎样学会写代码，再讲怎样评估生成的代码，然后讲 Agent 式编程的工作方式、工具和训练，最后扩展到前端开发和更广的软件工程任务。

二、会写代码的模型

1. 写代码需要什么能力

根据提示写代码需要三方面能力：语言，包括语法、API 和惯用写法；编辑，能同时参考空缺前后两边的代码；推理，从需求说明推出程序应该有的行为。

训练一个代码模型通常分三个阶段：预训练，在包含代码的大规模语料上训练；中期训练，加大代码比例，拉长上下文；强化学习后训练，训练推理能力，用执行结果作为奖励。

2. 预训练：从代码和文字中学习

预训练的目标和普通语言模型一样，最小化下一个 token 的预测损失：

$$\mathcal{L}_{LM} = -\mathbb{E}_{x\sim D_{mix}} \sum_t \log p_\theta(x_t \mid x_{<t})$$

其中 $D_{mix}$ 是混合数据：网页文本、技术文章、数学、源代码和文档。要保留代码的结构，包括缩进、文件边界、API，以及文字和代码之间的关系。训练过程中要评估：按领域分别看留出数据上的损失，再加上实际能否写出能运行的代码（参考 OLMo，Groeneveld 等，2024）。

数据的选择和清洗（参考 StarCoder）包括四件事：按语言和来源过滤，去掉自动生成的数据转储、编码损坏的内容和低价值的重复；去重，包括 fork 出来的仓库、项目里附带的第三方库、几乎相同的文件、到处复制的题解；控制来源，记录许可证、日期、作者选择退出的情况，过滤敏感数据；防止泄漏，按仓库或题目族划分训练和测试，并把评测题从训练数据中清除。

3. 代码的分词

代码的分词器要在代码和文字上一起学字节级 BPE 子词，变量名可能被拆成多个 token。空白字符必须保留，因为空格、制表符和换行在 Python 这类语言里本身就是语法。连续的空格要合并成一个 token，否则每个空格占一个 token，非常浪费。幻灯片展示了 StarCoder2 的真实切分：if ready: 换行后缩进四格 return value，切成 if、 ready、:、换行加三个空格、 return、 value、换行。

4. 大规模代码预训练的例子

StarCoderBase（Li 等，2023）有 155 亿参数，训练了 1 万亿 token，覆盖 80 多种编程语言，数据包括源码、issue、commit 和 notebook。随着训练 token 增加，大多数语言的 pass@1（一次生成就通过测试的比例）都在上升。

5. 中期训练：加更多代码

在已有模型基础上继续训练，提高代码比例，同时保留文字和数学数据。比例要靠实验选：比较代码能力的提升和通用能力的保持。Code Llama 在 Llama 2 的基础上额外训练了 5000 亿 token，得到 7B、13B、34B 三个版本，然后再做上下文扩展。

Qwen2.5-Coder 的实验（论文表 3）显示了混合比例的影响：

代码 / 文字 / 数学常规代码任务MATHMMLU

加入 30% 的文字和数学，代码分数只降了 1.5，数学和通用知识却大幅提高。

处理长输入时，训练序列要把相关文件连起来，保留路径和跨文件依赖。比如 types.py 里定义 Result.value 可能是 None，worker.py 把 Result 传下去，caller.py 要补上空值检查。Qwen2.5-Coder 训练时从 8K 拉到 32K，再用 YaRN 扩展到 128K（第三讲讲过）。要验证跨文件补全、填空，以及短上下文能力没有退化。

6. 填空：同时利用空缺前后的代码

普通语言模型只能从左往右写。但编辑代码时，经常要在中间补一段，而后面的代码提供了重要线索。比如 def is_positive(x: int) -> ____: 下一行是 return x > 0，看到函数体返回的是比较结果，就能推出返回类型是 bool。

InCoder（Fried 等，ICLR 2023）的训练方法是：把原始代码切成前缀、一段内容、后缀，把中间那段挪到最后，用一个标记符号 [M0] 占位：训练序列是"前缀 [M0] 后缀 [M0] 内容 [END]"。这样模型仍然是从左往右生成，但生成中间内容时已经看过了后缀。推理时给"前缀 [M0] 后缀 [M0]"，让模型生成内容。可以有多个空缺，每个用不同的标记。这样模型不需要专门训练，就能做补全代码、推断类型、生成注释、重命名变量等编辑任务。

从代码中学习还有其他方式：commit 差异，给修改前代码和提交信息，预测修改后的代码（OctoPack）；诊断信息，给出错代码和报错，预测修复（DrRepair）；测试，用程序的测试结果作为奖励（CodeRL）；执行轨迹，预测程序执行了哪些行、各变量的状态（CodeExecutor）。

三、怎样评估生成的代码

1. 和参考答案比文字

最直接的方法是和参考答案比较：精确匹配，或者 BLEU-4（统计连续 4 个 token 片段的重合度，并惩罚过短的输出）。问题是文字相近不等于行为相同。判断整数是否为正，参考答案是 return x > 0；return x >= 0 只差一个字符，但 x 为 0 时就错了；return not (x <= 0) 写法完全不同，对整数却完全等价。CodeBLEU（Ren 等，2020）加入了语法树和数据流的比较；CodeBERTScore（Zhou 等，EMNLP 2023）用预训练模型把代码编码成向量，逐个 token 找最佳匹配，算出精确率、召回率和 F 值。

2. 运行代码检查行为

更可靠的做法是运行。候选代码 return x >= 0，测试输入 −1、0、1，期望输出 False、False、True。在隔离环境中运行，限制时间和内存，比较输出：输入 0 时实际返回 True，失败，因为 0 不是正数。

好处缺点或局限
接受各种不同的正确写法有限的测试可能漏掉错误行为
通过执行发现语义错误需要可信的测试、依赖和隔离执行环境
检查的是实际行为需要时间和稳定的运行环境

测试不充分的问题由 EvalPlus（Liu 等，2023）专门研究过。常用基准有：HumanEval，164 个 Python 函数，根据文档字符串补全，用隐藏单元测试检查；CodeContests，竞赛题（包括 Codeforces），根据题目写完整程序，编译并测试。

3. pass@k

pass@k 是采样 k 个程序、至少有一个通过全部测试的概率（Chen 等，2021）。k 越大，分数越高，它衡量的是"多试几次能不能做出来"。

4. 非功能性需求

有些要求不是"对不对"，而是"好不好"。比如"让这段代码更快"，修改后输出不变、耗时更少。NoFunEval（Singhal 等，2024）包含 397 个代码编辑任务，按需求类型用不同方式检查：运行效率，跑测试并计时，按加速比打分；延迟或资源占用，和参考修改比较，用 DiffBLEU 打分；可维护性和安全，用 CodeQL 做静态检查，再乘以和参考修改的匹配度。

5. 从测试结果中学习

DeepCoder（Luo 等，2025）用执行结果做强化学习：对每道题采样若干个回答（推理加最终代码），运行测试，通过就给奖励，然后更新模型，让得到奖励的回答更可能出现，再用更新后的模型重新采样。

课上用一个例子说明推理为什么重要：计算 1 + … + n，n 最大到 1012。逐个相加 sum(range(n + 1)) 结果对但太慢。把首尾配对推出公式，并用 0 和 1 验证，得到 n * (n + 1) // 2，又对又快。如果只是凭记忆写公式，可能抄错成 n * (n - 1) // 2，n = 1 时就错了。

DeepCoder 的训练中，RL 阶段的回答长度上限从 16K 提高到 32K，评估时再给 64K（不继续训练），在 LiveCodeBench 上的成绩逐步接近 o3-mini。

四、Agent 式编程

1. 从单步到多步

单步编程：一个自包含的提示，模型推理并写出代码，评估答案。Agent 式编程：给一个 issue 和已有的仓库文件，Agent 反复搜索、编辑、跑测试，最后交出补丁和证据。

2. 定位、编辑、验证的循环

课程用一个贯穿全讲的 bug 做例子：配置里把重试次数设为 0，程序却用了默认值 3。仓库里有 cli.py、config.py、test_config.py。

定位：零是在哪里变成默认值的？用 rg 'retries' 搜索，找到 return config.get("retries") or 3。在 Python 里 0 被当作"假"，所以 0 or 3 得到 3。先复现：运行对应的单元测试，得到 AssertionError: 3 != 0。现在要修的是这个判断条件，不是去改测试。

编辑：只有值为 None 时才用默认值。 

# 修改前：所有"假"值都会变成默认值
return config.get("retries") or 3

# 修改后：显式设置的 0 能保留下来
value = config.get("retries")
return 3 if value is None else value

验证：跑已有测试，缺失时得 3，None 得 3，零得 0，正数得 2，4 个测试全部通过。如果零仍然变成 3，就回去继续定位值在哪里被改掉；如果某个默认情况坏了，就改规则再验证。失败会修正你的假设，推动下一轮循环。这个循环的概念来自 SWE-agent。

3. 另一种选择：固定工作流

Agentless（Xia 等）不让模型自由决定下一步，而是由开发者写死一个流程：先分层定位（文件、类或函数、具体位置），再生成多个候选修复，最后用测试筛选。上一讲说过，事先固定流程更便宜、更可预测。

五、编程 Agent 的工具

1. 只给一个 shell

mini-SWE-agent 只提供一个 bash 接口，模型每次选一条命令：读和搜索用 rg、cat、find；编辑用 sed、Python 脚本或 patch；执行检查用 pytest 或构建命令。返回的是输出、退出码，以及是否超时。用 sed 改文件的例子： 

sed 's/^RETRIES = 3$/RETRIES = 5/' settings.py > settings.new
mv settings.new settings.py

2. 专门的编辑格式

  • 整个文件重写：简单，但未改动的代码也要重复输出一遍。Pi 和 OpenCode 的 write、OpenHands 的 create 属于这种。
  • 搜索替换：只发送旧内容和新内容，简洁，但旧内容必须在文件中唯一匹配。OpenHands、Pi、OpenCode 的 edit 属于这种，Aider 用 <<<<<<< SEARCH … ======= … >>>>>>> REPLACE 标记。
  • 统一 diff（unified diff）：标准格式，带行号和上下文行。Aider 的变体省略了行号。
  • 文件操作补丁：Codex 的格式，用 *** Begin Patch、*** Update File: 标出文件操作，只带上下文，不带行数。OpenCode 和 OpenHands 根据预设也会用它。

编辑格式的影响可能很大。Aider 的重构基准包含 89 个 Python 任务，要求把大类里的一个方法移到顶层函数，检查语法和代码是否保留完整。用 GPT-4 Turbo（gpt-4-1106-preview）时，搜索替换格式成功率 20%，简化的统一 diff 格式 61%。

3. 找到相关的代码

从症状入手时，一个命令行参数、一个配置加载器、一个重试循环可能都能匹配上"retries"。要跟着值走：配置输入在哪里第一次读到零？默认值逻辑在哪里把零变成三？LocAgent（Chen 等，2025）把代码组织成依赖图：config.py 里的 retry_count 被 cli.py 调用，被 test_config.py 测试，结果被 client.py 的重试循环使用。先检索相关的邻近节点，再用执行来确认。

六、评估和训练编程 Agent

1. SWE-bench 怎样评估

SWE-bench（Jimenez 等）从真实 GitHub issue 和对应的修复 PR 构建任务。评估看两类测试：原本失败、修复后应该通过的测试（验证要求的修复完成了）；原本通过、修复后仍要通过的测试（验证没有破坏已有行为）。

2. 构建可运行的训练任务

一个可运行的任务包含：起始状态（文件、依赖、测试命令）；issue（要求的行为和复现方式）；检查（bug 在修复前失败，修复后行为恢复）。在收集训练轨迹之前，要先验证环境本身是可用的（SWE-Gym）。

3. 多步修复的强化学习

R2E-Gym（Jain 等，2025）的设定：模型的动作（搜索找到 config.py、编辑保留零、测试和结束）是训练目标；找到的文件、应用的补丁、测试输出只是上下文。最后只有一个终局奖励：修好了没有。目标是最大化轨迹的期望奖励 $\max_\theta \mathbb{E}_{\tau\sim\pi_\theta}[R(\tau)]$。难点是：最后失败了，并不能告诉你前面哪一步决策错了。

SWE-Gym（Pan 等，2024）在 32B 模型上研究了两个方向的扩展：增加训练数据，以及推理时用学出来的验证器从多个候选中挑选。

4. 通过注入 bug 制造任务

真实的 issue 数量有限。SWE-smith（Yang 等，2025）反过来做：从一个能运行、测试全通过的代码库出发，修改代码（不改测试），保留那些让测试新出现失败的修改。例子：原来 4 个测试全过；把条件改成 return 3 if not value else value，零又变成了三，3 过 1 失败；恢复后 4 个全过。这样就得到了一个有明确答案的修复任务。

5. 多语言和多 Harness

不同语言的项目结构不同：Python 有 pyproject.toml，用 pytest；TypeScript 有 package.json，用 npm test；Rust 有 Cargo.toml，用 cargo test。Agent 要先读项目配置，再决定用什么构建和测试命令。相关基准有 Multi-SWE-bench 和 SWE-bench Multilingual。

Harness 等于提示词、工具、Agent 循环和上下文管理的组合。同一个模型如果只在一种 Harness 里训练，换一种可能表现变差。Nemotron 3 Ultra 对每类任务至少用两种 Harness 训练；Polar 让 OpenHands、OpenCode、Codex 等原生 Harness 都通过一个共享的模型 API 代理调用同一个模型，收集轨迹和奖励来更新模型。

七、前端开发

前端 Agent 的循环多了一个在浏览器中验证的环节：定位组件和事件处理函数；修改逻辑和样式；在浏览器里操作（输入、点击、检查保存的状态），并截图查看渲染后的页面；检查失败就修改。SWE-bench Multimodal（Yang 等，2024）给 SWE-agent 加上了浏览器和截图工具。

验证有两种方式。浏览器 Agent 每一步由模型决定下一个动作，适合探索（下一讲的内容）。Playwright 脚本由模型写一段可重复运行的检查：在 Name 里填空格，点保存，断言保存的状态，截图。截图可以交给模型看，也可以和人工批准过的基准截图比较。

课上的例子：修复前，空白名字也能保存成一条记录；把 value.length 改成 value.trim().length 后，空白名字被拒绝。行为检查：没有新增记录，合法名字仍能保存。外观检查：错误提示显示在 Name 旁边，清晰可读。

SWE-bench Multimodal 的 issue 里带有图片，但评分依据仍然是测试：空白名字会报错且不新增记录，合法名字能保存，已有测试全部通过。issue 里有图片，不代表要用图片相似度来评分。

八、更广的软件开发

修 bug 只是软件开发的一环。完整流程是：需求（用户需要什么、兼容性）；实现循环（编辑、测试）；评审（diff 和证据）；发布决定；部署和监控（线上信号、回滚方案）；维护（新需求、发现的故障）。测试通过只是其中一步，不等于可以发布。

Meyer 等（2019）统计了 5,928 个微软开发者自报的工作日：真正写代码（读写代码和测试）只占 15%，其余 85% 是会议和邮件、调试、跑测试、代码评审、需求和文档、帮助同事、学习和行政事务、休息等。

  • 应用创建和修改（ViBench）：从零构建新应用 15 个；在参考 MVP 上扩展 45 个；在 Agent 自己之前做的 MVP 上扩展 45 个。每个结果都用人写的浏览器测试计划检查。

  • 维护（SWE-Milestone，2026）、测试生成（SWT-Bench，Mündler 等，2024）。
  • CI 修复（LCA CI Builds Repair）：构建失败报 EBADENGINE，因为运行环境是 Node 16，而包要求 Node 18 以上。要检查包支持的运行时，把 setup-node 配置改成 20，然后重新安装、构建和测试。

九、预测代码行为的模型

Agent 有一个策略 $\pi(a \mid h)$：根据历史（看过的代码、工具结果）选择动作，比如"运行测试"，然后在真实环境中执行，观察到"断言失败"。也可以有一个世界模型 $p(o \mid h, a)$：不真正执行，而是预测执行结果。预测可能出错，而且预测也受历史影响。

预测执行的一个难点是共享引用： 

items = [1]
alias = items
alias.append(2)
result = len(items)

正确结果是 items 和 alias 都是 [1, 2]，result 为 2。如果把 alias 当成一个副本，就会错误地预测 result 为 1。

预测在什么时候对 Agent 有用？假设有两个修复，A 是对的，B 是错的。模型预测 A 会失败、B 会通过，Agent 就会选 B 丢掉 A。所以要把两个候选都真正运行一下，检查模型判断得对不对，并且同时比较任务成功率和总延迟、token、工具调用次数。

相关工作有 CWM（FAIR CodeGen 团队，2025），从程序执行中学习；Code World Models / GIF-MCTS（Dainese 等，2024），构建和使用模拟器。开放问题包括：在同一批问题上同时测量预测误差和任务成功，看决策是否真的变好；把延迟、token 和真实环境调用算进成本；在留出的程序、依赖和环境上测试泛化；改变"何时退回真实执行"的阈值，同时测量失败和节省。

十、小结

设计编程 Agent 涉及六个方面：代码模型，经过预训练、中期训练和基于执行奖励的 RL；Agent 式编程，用合适的工具完成定位、编辑、验证；Agent 训练，需要可运行的任务、修复奖励和多样的 Harness；前端开发，需要浏览器交互和视觉验证；更广的开发任务，包括定位、应用、写库、维护、测试和 CI；代码行为预测，用学出来的模型辅助执行和规划。
